## 1. 蓝牙 BLE

### 1.1 广播 ID

广播数据：

```text
'T', 'R', 0x00, 0x83, CID1, CID2, PID, 0x00, DEV_TYPE
```

- `CID1`、`CID2` 和 `PID`：客户编号信息，以实物为准，App 可以不过滤这些字段。
- `DEV_TYPE`：设备尺寸。

| DEV_TYPE | 屏幕尺寸 |
|---:|---|
| `0` | 32×32 |
| `1` | 52×52 |
| `2` | 78×78 |
| `3` | 104×104 |

App 通过过滤广播包显示搜索到的 BLE 设备。

### 1.2 广播设备名

```text
PDD_xxxxxx
```

后缀 `XXXXXX` 为 BLE MAC 地址。原文使用 6 个占位字符，没有进一步规定完整 MAC 字符数和分隔符形式。

### 1.3 服务与特征 UUID

| 用途 | 16 位 UUID | 标准 128 位展开 |
|---|---|---|
| 主服务 | `0x00FA` | `000000fa-0000-1000-8000-00805f9b34fb` |
| Write，手机向硬件传输 | `0xFA02` | `0000fa02-0000-1000-8000-00805f9b34fb` |
| Notify，硬件向手机传输 | `0xFA03` | `0000fa03-0000-1000-8000-00805f9b34fb` |

Notify 特征包含 `0x2901`（Characteristic User Description）和 `0x2902`（Client Characteristic Configuration）描述符。

### 1.4 大数据 BLE 写入分片

当一帧数据超过单次 BLE 写入能力时，需要从帧的第一个字节开始连续分片发送，直到整帧发送完成。协议举例：一帧总长度为 `0x100F`，假设 MTU 可承载 512 字节，则每次写 512 字节。

在整帧尚未发送完成时，即使该命令定义了响应，硬件也不会提前反馈。

> 上位机实现把“单次可写字节数”作为参数。实际联调时应传入协商后的有效 ATT 载荷，不能把 BLE MTU 数值直接等同于可写载荷。`PDD_CB724E` 实测 MTU 为 512，Write Without Response 有效载荷为 509 字节。

## 2. 通用数据格式

```text
Byte(0), Byte(1), Byte(2), Byte(3), Byte(4) ... Byte(N-1)
[       数组长度       ] [       类型       ] [命令字段和实际数据...]
```

- 数组长度：2 字节，小端，表示整帧总长度，包含长度字段自身。
- 类型：2 字节，小端。
- 原文还给出一个 9 字节扩展包头：`[长度:2][类型:2][A:1][B:4]`。
- `A`：1 字节，含义随命令变化。
- `B`：4 字节，小端，含义随命令变化。
- 从 Byte 9 开始的实际数据最大为 4096 字节。

短控制命令可以只有 `[长度][类型]` 或 `[长度][类型][A]`，不强制补齐 9 字节。

## 3. 获取硬件信息并同步时间

- 类型：`0x8001`

手机请求：

```text
[长度:2] [类型 0x8001:2] [时:1] [分:1] [秒:1] [预留:1，固定 0]
```

硬件响应：

```text
[长度:2] [类型 0x8001:2] [设备类型:1] [显示角度:1] [密码标志:1] [亮度:1]
```

原 PDF 的字段列表只有 7 字节，但长度写为 8。固件 3.9 实测 7 字节请求无响应，补 1 字节 `0` 后正常返回，因此上位机固定发送 8 字节请求。

设备类型见 1.1。显示角度：`0` 为 0°，`1` 为 90°，`2` 为 180°，`3` 为 270°。密码标志为预留字段。

## 4. 基础控制命令

### 4.1 删除全部数据

- 类型：`0x8003`

```text
请求：[0x04, 0x00, 0x03, 0x80]
响应：[0x05, 0x00, 0x03, 0x80, A]
```

`A=1` 删除成功，`A=0` 删除失败。

### 4.2 设置亮度

- 类型：`0x8004`

```text
请求：[0x05, 0x00, 0x04, 0x80, A]
响应：[0x05, 0x00, 0x04, 0x80, A]
```

请求 `A` 的有效范围为 10～100。响应 `A=1` 设置成功，`A=0` 设置失败。

### 4.3 获取版本号

- 类型：`0x8005`

```text
请求：[0x04, 0x00, 0x05, 0x80]
响应：[0x08, 0x00, 0x05, 0x80, A, B, C, D]
```

- `A.B` 组成 MCU 版本号。例如版本 1.0：`A=1`、`B=0`。
- `C`、`D` 组成客户编号，其中 `C` 为 CID，`D` 为 PID。

### 4.4 设置屏显旋转

- 类型：`0x8006`

```text
请求：[0x05, 0x00, 0x06, 0x80, A]
响应：[0x05, 0x00, 0x06, 0x80, A]
```

请求 `A`：`0` 不旋转，`1` 旋转 90°，`2` 旋转 180°，`3` 旋转 270°。响应 `A=1` 设置成功，`A=0` 设置失败。

## 5. DIY 临时图片

- 类型：`0x0000`

请求：

```text
[长度:2] [类型 0x0000:2] [A:1] [B 图片总长度:4] [图片数据...]
```

- `A=0`：图片首包。
- `A=2`：后续图片数据包。
- `B`：整张图片的字节长度，小端。例如 104×104 RGB888 为 `104×104×3=32448` 字节。
- 32×32、52×52 屏发送 PNG 文件；78×78、104×104 屏发送 RGB 数据。

响应：

```text
[长度:2] [类型 0x0000:2] [A:1]
```

| A | 含义 |
|---:|---|
| `3` | 传输命令有效 |
| `0` | 传输命令无效 |
| `2` | 空间不足，保存的数据无效 |
| `1` | 保存成功 |

## 6. 保存图片文件

- 请求类型：`0x0002`

请求：

```text
[长度:2] [类型 0x0002:2] [A:1] [B 文件总长度:4]
[C CRC32:4] [D:1] [列表序号:1] [图片数据...]
```

- `A=0`：创建图片文件的首包。
- `A=2`：后续图片文件数据包。
- `B`：完整图片文件字节数，小端。
- `C`：图片文件的 32 位 CRC 校验值。原文未规定字节序；上位机当前按小端编码，待联调确认。
- `D`：原文列出该字段，但未说明用途。
- 列表序号：1～10。
- 32×32、52×52 屏发送 PNG 文件；78×78、104×104 屏发送 RGB 数据。

原文响应示例：

```text
[0x05, 0x00, 0x01, 0x00, A]
```

| A | 含义 |
|---:|---|
| `1` | 传输命令有效 |
| `0` | 传输命令无效 |
| `2` | 空间不足，保存的数据无效 |
| `3` | 整个文件保存成功 |

## 7. 进入/退出画板

- 类型：`0x0104`

```text
请求：[0x05, 0x00, 0x04, 0x01, Type]
响应：[0x05, 0x00, 0x04, 0x01, A]
```

| Type | 行为 |
|---:|---|
| `0` | 退出画板，不保存 DIY 内容，并恢复进入 DIY 前的显示内容 |
| `1` | 进入画板，并清空当前显示 |
| `2` | 退出画板，仍显示 DIY 内容 |
| `3` | 进入画板，不清空当前显示 |

响应 `A=1` 表示传输 OK，`A=0` 表示传输无效。

实机核对：104×104 的 `PDD_CB724E` 返回类型为 `0x0107`。DOCX 第 4 页把响应示例写成了 `0x0207`，与同页请求、PDF 第 4 页及实机回包不一致，按笔误处理。

## 8. 发送实时画板数据

- 类型：`0x0105`

普通效果：

```text
[长度:2] [类型 0x0105:2] [Type:1] [R:1 G:1 B:1]
[点1列:1 点1行:1] [点2列:1 点2行:1] ...
```

整体移动（`Type=3`）：

```text
[长度:2] [类型 0x0105:2] [0x03] [上:1] [下:1] [左:1] [右:1]
```

| Type | 效果 |
|---:|---|
| `0` | 无效果/普通画笔 |
| `1` | 水平镜像 |
| `2` | 垂直镜像 |
| `3` | 整体移动 |
| `4` | 橡皮擦 |

- `RGB`：当前画笔颜色，RGB888。
- 行列序号范围随屏幕尺寸变化；104×104 屏为 0～103。
- 原文红色公式明确把每个点编码为“列序号、行序号”。

## 9. 发送高亮画板数据

- 类型：`0x0109`

```text
[长度:2] [类型 0x0109:2] [Type:1] [R:1 G:1 B:1]
[点1列:1 点1行:1] [点2列:1 点2行:1] ...
```

- `Type=0`：首包。
- `Type=2`：后续包。
- 坐标数据超过 4096 字节时分包。
- 硬件不回复该指令，每个协议数据包之间至少间隔 50ms。
- 仅 78×78 和 104×104 屏使用该指令；32×32 和 52×52 屏使用 `0x0000` 发送 PNG 文件。

## 10. 开关屏幕显示

- 类型：`0x0107`

```text
请求：[0x05, 0x00, 0x07, 0x01, A]
响应：[0x05, 0x00, 0x07, 0x01, A]
```

请求 `A=0` 关闭显示，`A=1` 打开显示。响应 `A=1` 表示传输 OK，`A=0` 表示传输无效。

## 11. 原文歧义与下位机联调确认项

以下问题在 PDF 中没有唯一答案，上位机代码没有静默掩盖这些差异：

1. 同步时间请求示例的长度字节写成 `0x0008`，但示例只列出 7 个字节。上位机当前遵循“长度等于实际帧总长”的通用规则，编码为 `0x0007`。
2. 数据格式称 Byte 0～8 为固定 9 字节包头，但删除、亮度、版本、旋转等命令明确使用 4～5 字节短帧。上位机采用最小 4 字节通用头，命令字段按需追加。
3. 保存图片请求类型为 `0x0002`，响应示例类型却是 `0x0001`。响应解析前必须在联调时确认真实下位机返回类型。
4. 保存图片字段 `D` 未定义。上位机保留 1 字节参数，默认发送 `0x00`。
5. PDF 仅写“32 位 CRC”，未指定字节序、多项式、初值、反射、结果异或等参数。上位机暂按小端提供 CRC-32/IEEE 默认实现，但下位机联调必须确认。
6. 实时画板的文字说明同时出现“行、列”和“列、行”。上位机按红色公式使用 `[列, 行]`。
7. “MTU=512，每次发送 512 字节”是文档示例。真实 BLE 写入长度必须根据平台协商结果设置。
8. 原文未说明图片 RGB 数据的排列。参考 APP 的 `BGRUtils.bitmap2RGB` 按 Bitmap 行优先顺序输出 `R、G、B`，104×104 上位机据此发送 RGB888；旋转后的坐标系以及 PNG 编码限制仍需分别联调。

## 12. 上位机实现与测试范围

已实现：

- 广播签名、客户字段、设备类型和 `PDD_` 设备名解析。
- 服务、Write、Notify UUID 常量。
- 小端长度/类型帧编解码与长度校验。
- 时间同步、清空、亮度、版本、旋转、画板模式、实时画笔、屏幕开关命令。
- DIY 图片、保存图片、高亮画板的 4096 字节协议分包。
- 保存图片 CRC-32/IEEE、预留字段和 1～10 列表序号。
- BLE 单次写入分片及高亮帧 50ms 间隔发送器。
- 硬件信息、版本和通用状态响应解析。

本轮未做：

- 不连接真实 BLE 设备。
- 不替换现有生产 BLE 适配器。
- 不对 PNG/RGB 实际屏显效果作下位机结论。
- 不验证 ACK 时序、CRC 参数和保存图片响应类型。
